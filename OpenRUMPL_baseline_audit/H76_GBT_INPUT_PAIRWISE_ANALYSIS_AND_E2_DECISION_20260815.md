## 3. 为什么本次 H76 没有直接加入 E2

这次 R0/H76 的目的，是在**相同 GBT-style 输入下锁定坐标级主干基线**，并为
B1/B2 分离“训练量/视角采样协议”的影响。H76 是 `run/train_rumpl.py` 中的直接
3D 回归模型；E2 不是一个可由环境变量打开的同一前向分支，而是：

1. 先离线生成 H76/RIGR、DLT/IRLS、pairwise 等多组三维候选；
2. 再训练 Set Transformer / joint-level counterfactual utility scorer；
3. 最后按每个关节选择或融合候选。

直接把 E2 混进本次 H76 会同时改变候选池、训练目标、模型输出路径和训练数据，
无法判断 B1/B2 的 300k 更新或 GBT 视角协议到底带来什么影响，所以本轮有意隔离，
不是认为 E2 无效。

已有 E2 数字来自另一条输入/候选协议：旧的 RIGR→E2（A1D/H21、注释框）在
V3/V4 为 **28.555/27.808 mm**，且早期只训练 V3/V4；延长到 30 轮后 S9/S11
仅再改善约 0.009/0.012 mm，说明该模型已基本饱和。它不能直接当作当前
GBT-style H76 的 V2 结果，也不能把旧数字和本表混成同一公平主表。

## 4. E2 是否应该继续纳入

应该继续，但要重建为当前输入协议下的独立实验：

1. 用当前 GBT-style H76 射线缓存对所有 V2/V3/V4 子集生成候选：H76、
   confidence-weighted DLT、IRLS、pairwise hypotheses；候选生成不读取 GT。
2. 先做零训练 oracle：重点检查 `1-4`、`2-3` 是否至少出现 0.3 mm 以上的
   互补改善；若 oracle 不改善，E2 scorer 没有可学习的候选增益。
3. 通过 oracle 后训练 E2-V234 universal，并与 V34 specialist、当前 H76 做
   同缓存、同 S9/S11、同 action-equal All-17 对照。
4. 先做短筛选，再决定是否扩展到长预算；不能把旧 E2 的 V3/V4 specialist
   结果直接宣称为当前 H76 的融合结果。

结论：当前 46.23 mm 的 V2 瓶颈已经定位为 `1-4`/`2-3` 退化相机对。E2 值得
加入，但正确顺序是“当前输入重建候选池 → oracle → E2-V234”，而不是把旧 E2
checkpoint 直接拼到正在进行的 H76 训练中。
